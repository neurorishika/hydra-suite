# Publishing to PyPI

How to release new versions of hydra-suite to PyPI.

!!! warning "Not yet published"

    hydra-suite has **not** been published to PyPI yet (`pip install
    hydra-suite` returns "not found"). Users install with `install.py` from a
    checkout or a git URL; see [Installation](../getting-started/installation.md).
    This page describes the release process for when it is published. Even
    then, a plain `pip install` will not give a complete install: it cannot
    choose the right torch build, and it cannot install the git-only CLIP
    fork or the AprilTag fork. Keep `install.py` as the documented path.

## Prerequisites

`build` and `twine` are included in dev dependencies. Install them with:

```bash
make install-dev            # into the activated env, with the tested pins
# or
python install.py --dev     # full install including dev tools
```

You also need a [PyPI account](https://pypi.org/account/register/) and an [API token](https://pypi.org/manage/account/token/) (unless using trusted publishing via GitHub Actions).

## Release workflow

### 1. Update the version

Edit `pyproject.toml`:

```toml
version = "1.1.0"
```

This is the single source of truth — `__init__.py` reads it via `importlib.metadata` at runtime.

### 2. Build

```bash
rm -rf dist/ build/
python -m build
```

This produces both a `.whl` (wheel) and `.tar.gz` (sdist) in `dist/`.

### 3. Inspect the wheel

```bash
# Check size (should be ~1-2 MB)
ls -lh dist/*.whl

# Verify bundled assets are included
unzip -l dist/*.whl | grep -E "(resources/brand|resources/configs|py\.typed)"

# Verify old brand/ directory is NOT included
unzip -l dist/*.whl | grep "^.*brand/" | grep -v "hydra_suite/resources"
```

### 4. Test on Test PyPI (first release or major changes)

```bash
twine upload --repository testpypi dist/*

# Test in a clean environment
python -m venv /tmp/hydra-test
/tmp/hydra-test/bin/pip install --index-url https://test.pypi.org/simple/ \
    --extra-index-url https://pypi.org/simple/ \
    hydra-suite
/tmp/hydra-test/bin/python -c "from hydra_suite.paths import get_brand_icon_bytes; print('OK')"
```

### 5. Upload to PyPI

```bash
twine upload dist/*
```

### 6. Tag the release

```bash
git add pyproject.toml
git commit -m "release: v1.1.0"
git tag v1.1.0
git push origin main --tags
```

## Automated publishing (recommended)

Instead of manual uploads, use GitHub Actions with trusted publishing. This eliminates API tokens.

### Setup (once)

1. On PyPI, go to your project → Settings → Publishing → Add trusted publisher
2. Enter your GitHub repo owner, name, workflow filename, and environment name

### Workflow

Create `.github/workflows/publish.yml`:

```yaml
name: Publish to PyPI
on:
  release:
    types: [published]

permissions:
  id-token: write

jobs:
  publish:
    runs-on: ubuntu-latest
    environment: release
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: pip install build
      - run: python -m build
      - uses: pypa/gh-action-pypi-publish@release/v1
```

After this, creating a GitHub release auto-publishes to PyPI.

## What goes in the wheel

The wheel includes:

- All Python source under `src/hydra_suite/`
- `hydra_suite/resources/brand/*.svg`, `*.png` — app icons
- `hydra_suite/resources/configs/*.json` — default presets
- `hydra_suite/resources/configs/skeletons/*.json` — skeleton definitions
- `hydra_suite/py.typed` — type checker marker

The wheel does **not** include:

- `src/brand/` (original brand assets with `.ai` source files — excluded via `pyproject.toml`)
- `configs/` at repo root (bundled copies are in `resources/`)
- `models/`, `training/` (user data, lives in user home directory)
- `tests/`, `docs/`, `legacy/`, `tools/`

## Dependency architecture

```
pyproject.toml [project.dependencies]          <- the ONLY declaration of Python deps
    numpy, scipy, PySide6, ultralytics, sam2, torch>=2.4, torchvision>=0.16, ...

pyproject.toml [project.optional-dependencies]
    cpu / mps / cuda12 / cuda13   tier extras (install.py selects exactly one)
    cuda                          alias for cuda12
    sam (sam3 alias)              SAM3 inference helpers, installed on every tier
    sam3-train                    SAM3 training sidecar only, never the main env
    dev / docs / onnx-tools

constraints/*.txt                              <- tested pins, generated by tools/lock_constraints.py
install.py                                     <- torch build + index, CLIP and AprilTag git installs,
                                                  platform fixups, sidecar envs
```

**torch** is declared in `pyproject.toml` with a loose floor (`torch>=2.4`).
`install.py` installs a pinned build (`TORCH_VERSION`) from the PyTorch wheel
index for the tier *before* resolving hydra-suite, and constrains the
resolver so it is never swapped. PEP 621 cannot express per-dependency index
URLs, which is why this step lives in the installer.

**CLIP** (SAM3's text encoder) is not a dependency at all. It is a PEP 508
direct reference (`clip @ git+https://...`), which PyPI rejects in uploaded
metadata, so listing it would break `twine upload` for the whole package.
`install.py` installs it from a pinned commit.

When adding new dependencies:

- **Needed by every install** → `[project.dependencies]`
- **Tier-specific** (e.g. CUDA-only wheels) → the matching tier extra(s)
- **Git-only or index-specific** → a step in `install.py`, not `pyproject.toml`
- Then regenerate the pins: `python tools/lock_constraints.py`. See
  [Dependency and CUDA Updates](dependency-cuda-updates.md).

## Version checklist

Before releasing:

- [ ] Version bumped in `pyproject.toml`
- [ ] Changelog updated
- [ ] `make format && make lint` passes
- [ ] `python -m pytest tests/` passes
- [ ] Wheel builds cleanly: `python -m build`
- [ ] Wheel assets verified: `unzip -l dist/*.whl | grep resources`
- [ ] Test install in clean venv works
